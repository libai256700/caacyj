## 是否适合替换 deepseek 通道

结论：可作为外部候选能力做适配评估，不可直接替代当前 Java DeepSeek 主链路。

原因：

- 可行点：
  - 前端最后一步已经存在完整远程生成链路：`POST /api/save` -> `GET /api/check/{id}` -> `GET /reports/{id}.html`。
  - 接口返回结构简单，接入成本低。
  - 本次测试可生成完整报告，说明目标服务当前可用。
- 主要顾虑：
  - 未发现鉴权与访问控制，报告 ID 直连可读，存在数据泄露和被枚举风险。
  - `POST /api/save` 会产生真实报告数据，当前未确认调用授权、频率限制、并发限制和可商用边界。
  - 报告内容由对方服务生成，稳定性、可控性、审计能力和失败兜底机制未知。
  - 目标 HTTPS 首次访问曾出现 `net::ERR_CERT_COMMON_NAME_INVALID`，虽然后续页面成功打开，但证书配置仍是接入风险。
  - 当前仓库自测报告主链路是 `FrontPracticeServiceImpl -> DeepSeekOpenAiClient.complete(...)`，期望后端 Bearer 鉴权的 OpenAI Chat Completion 契约和可解析 JSON；目标服务是匿名表单提交 -> 异步生成 -> HTML 报告落地，至少需要适配层转换输入、轮询状态、解析 HTML/报告内容并补充 fallback。

建议：

- 如果只是内部临时自测：可以作为临时外部报告通道接入，但应限制样本数据为非敏感测试值，并记录报告 ID。
- 如果要替换正式 deepseek 通道：不建议直接替换。应先取得接口授权，确认计费/限流/数据归属/隐私合规/可用性 SLA，并要求对方补充鉴权或由我方网关封装后再接入。
