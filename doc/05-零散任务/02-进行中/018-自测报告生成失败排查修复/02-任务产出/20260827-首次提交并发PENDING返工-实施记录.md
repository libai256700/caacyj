# 自测首次提交并发 PENDING 返工实施记录

## 根因

`FrontPracticeServiceImpl.submitAnswer` 原先先向 `yj_assessment_result` 插入 PENDING，再在异步入队方法中通过 `assessmentReportsInProgress.add(recordId)` 竞争单 JVM 生成资格。同一 `recordId` 的两个请求同时查不到既有结果时会各插入一行，竞争失败者没有异步任务承接；该行还可能成为最新结果，导致页面持续轮询 PENDING。

## 修复

- 注入 Spring `TransactionTemplate`，首次生成使用短事务取得数据库资格。
- 锁锚点为 `yj_user_practice_exercises_record.id`，锁 SQL 同时限定当前 `customer_account_id` 和未删除状态，并使用 `FOR UPDATE`。
- 行锁内二次查询最新结果：SUCCESS/PENDING 复用且不插入；FAILED 原地条件更新为 PENDING；不存在结果时才创建 PENDING。
- `TransactionTemplate.execute` 返回后才调用异步执行器，避免事务提交前任务读取不到 PENDING。
- 重生成沿用 FAILED 条件更新取得数据库资格，入队显式标记数据库资格已经取得，不受 JVM 内存状态影响。
- 执行器拒绝、入队异常或异步执行异常时，将已取得资格的 PENDING 更新为 FAILED。
- 已移除本地 `assessmentReportsInProgress`，非自测提交分支未改变。

## 边界

数据库行锁以练习记录为稳定锚点，可在多实例间串行化同一学员、同一记录的首次报告资格判断。本次未新增数据库索引、迁移或唯一约束，也未写入当前数据库。

进程在 PENDING 事务提交后、异步任务完成前崩溃时，仍可能留下陈旧 PENDING；当前没有租约时间、任务表或超时回收机制。本次只消除并发重复创建，不把进程崩溃恢复问题伪装成已解决。
