# 登录后一段时间自动退出排查结论

## 1. 当前问题分类

- 分类：鉴权链路问题，尚未完成运行库级最终确认。
- 真实入口：管理后台 `yunjikeji-admin-ui` 登录调用 `/system/auth/login`；后端使用 OAuth2 client `default` 创建 access token 和 refresh token。
- 用户侧表现：access token 到期后，请求返回 401；前端进入 refresh 流程，刷新失败时清理凭证并刷新页面，表现为自动退出并要求重新登录。

## 2. 最短证据链

1. `src/api/login/index.ts` 调用 `/system/auth/login`。
2. `src/config/axios/service.ts` 请求拦截器注入 `Bearer ACCESS_TOKEN`；401 分支调用 `/system/auth/refresh-token?refreshToken=...`。
3. 刷新失败进入 `handleAuthorized()`，清除本地 token 并刷新页面。
4. `OAuth2TokenServiceImpl` 按 `system_oauth2_client` 的有效期创建 access/refresh token；基线 SQL 中 `default` client 的 access token 有效期为 1800 秒（30 分钟），refresh token 为 2592000 秒（30 天）。
5. 运行环境数据库实际有效期、刷新失败响应和对应服务日志尚未核对，因此当前不能把基线 SQL 直接当作运行态事实。

## 3. 候选根因

### 高置信度：运行库 `default` client 的 token 有效期或刷新状态异常

如果运行库中的 `access_token_validity_seconds` 较短，或 refresh token 已过期/被删除，access token 到期后的刷新会失败；前端现有行为会清理 token 并强制回到登录页。这与“登录后一段时间自动退出”的时间型表现一致。

### 中置信度：无 refresh token 时刷新并发锁未复位

`service.ts` 的 401 处理在 refresh token 为空时直接走 `handleAuthorized()`；该分支可能绕过 `finally`，使 `isRefreshToken` 保持为 `true`，后续 401 请求进入排队/不再刷新，形成登录状态异常。需通过浏览器 Network 与 localStorage 复现确认。

### 中低置信度：刷新请求的租户上下文不完整

刷新请求依赖 axios 默认租户头；多租户环境若刷新接口还要求另一租户头，可能被服务端拒绝，随后触发强制重登。当前没有运行态请求头和响应证据，暂不定论。

## 4. 当前缺口与最短核对动作

1. 在实际测试环境只读查询 `system_oauth2_client` 中 `client_id='default'` 的两个有效期字段。
2. 用浏览器 Network 记录 access token 到期前后：原业务请求响应、refresh 请求的状态/响应、是否随后调用退出/清理逻辑。
3. 对照服务端 OAuth2 刷新失败日志，确认是 refresh token 过期、客户端不匹配、租户上下文失败还是其他错误。
4. 若运行态证明是前端无 refresh token 分支锁死，再单独建立实施变更和回归测试；本次未授权改代码。
