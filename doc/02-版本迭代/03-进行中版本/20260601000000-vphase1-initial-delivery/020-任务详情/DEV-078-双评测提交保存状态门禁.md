# DEV-078 双评测提交保存状态门禁

## 实施标准

- 上游规格：`REQ-052`、`PD-052` 与 `AC-ASSESSMENT-SAVE-001/101/201/301/401`。
- `yj_practice_catalog_batch.status` 固定为 `TINYINT NOT NULL DEFAULT 0`，取值仅允许 `0未开始 / 1写入中 / 2写入结束`；状态2只表示本次写入流程已经退出，不等于业务完成。兼容字段已由人工创建的现场，版本SQL必须幂等补齐定义；历史回填仅把 `is_completed=1` 作为只读筛选条件并只更新status，本任务不直接执行数据库变更。
- 主表 record 在开始答题时已经创建，`startBatch`、启动接口和主记录插入阶段不得置1。分类13/14均只在末题统一提交开始持久化第一条答案明细时，以条件更新把尚未完成批次由0置1；状态已为1的同页幂等重试继续写入，状态2不得回退为1。
- 两类评测完整保留各自既有完成流程：分类13原统一答案保存完成逻辑、分类14既有 report-entry 完成逻辑均不得修改；原流程完成后再执行只更新 `status=2` 的独立状态动作。DEV-078 不新增、替换、合并或修改任何 `is_completed` 判断、赋值、SQL或事务边界。
- 任一答案插入或持久化事务失败时，必须保留并继续返回原异常，同时在失败事务回滚之后通过独立事务只补偿写 `status=2`；补偿事务不得参加或依附原写入事务，绝不读取后改写或附带更新 `is_completed`，且不得因补偿成功而伪造业务完成。
- 首页用户在选择层点击“自我评测”或“职业规划评测”后，先通过各分类正式 latest-status 入口读取对应分类最新批次保存状态。`status=1` 时复用“是否需要重新测评”弹窗的视觉样式，固定提示“上次评测正在初始化分析，请稍后”；确认、关闭、遮罩或取消只关闭本提示，不得触发原重测 resolver、reset、start、查询后续链路或导航。
- `status=0/2` 时保持原 completed/restart/reset/start/navigation 判断和分类14 report-entry 语义；前端只拦截1，禁止把2直接解释为完成。分类13的变化严格限定为新增 `status=1` 前置门禁和保存状态跃迁，不扩大为逐题保存、续答或报告流程改造。
- 当前客户端在末题按逐题串行 HTTP 写入答案，进程或网络中断可能遗留 `status=1`。本轮不得擅自新增 TTL、状态3或批量新接口；同一答题页幂等重试必须能够继续写入并最终推进到2，该风险作为后续恢复设计输入。
- 不修改 `uni_modules/**`；先建立接口、数据、代码和交互红灯，再实施后端与前端，最后交由不同代理独立验收。
