### P0-3：config.json 重复 key — `models.pro`

```json
{
  "models": {
    "pro": { "name": "deepseek-chat", ... },      // ← 第一个
    ...
    "pro": { "name": "deepseek-v4-pro", ... }      // ← 第二个，覆盖第一个
  }
}
```

**危害：** Python 解析 JSON 时，后一个 `pro` key 会静默覆盖前一个。`models.pro` 的唯一入口变成了 `deepseek-v4-pro`，前一个 `deepseek-chat`（描述为 Pro 模式）完全失效。且 `model="deepseek-v4-pro"` 的 API 调用可能因模型名不存在而 404。

**建议：** 合并两个 `pro` 定义，或重新命名 key（如 `deepseek_pro` vs `deepseek_flash_pro`）。

## 🟢 优化建议 (P2)

### P2-1：逐个文件手动抽取 → 可半自动化

当前流程：老文指文件 → 分析 → 确认 → 抽取 → 复盘 → 确认 → 下一个。

**痛点：** 每次都要人工介入，文件量大时效率低。

**建议：**
1. **批量盲抽模式（仅高置信度文件）：** 对格式稳定的文件类型（岗位报告、题库），可一次选多个文件，改用批量处理 + 一次性复盘报告，而非逐个确认
2. **队列模式：** 构建一个抽取队列 JSON，脚本顺次执行，每次完成后自动生成复盘报告发老文，老文回复「继续」即推进
3. **文件类型预判自动化：** 利用文件内容 + 文件名做自动分类判断，跳过人工分析步骤（仅当置信度 < 0.8 时才问）
