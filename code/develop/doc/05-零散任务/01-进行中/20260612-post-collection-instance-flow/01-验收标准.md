# 岗位采集实例链路改造验收标准

## 业务验收

### A1 业务-交互线：立即采集和定时采集均形成可追踪任务实例
- 业务起点：已存在启用状态的岗位采集配置。
- 触发动作：后台点击立即采集，或定时任务扫描到应执行配置。
- 关键交互：系统创建一条 `yj_post_collection_task_instance` 记录，并把本次采集的岗位结果写入实例明细表。
- 业务终点：采集完成后，实例状态流转为成功已合入；采集失败时有失败状态和失败原因。
- 结果承接：管理端和后续数据排查可通过任务实例追踪本次采集数量、合入数量和失败原因。
- 核对方式：接口调用、定时任务执行记录、数据库记录和日志核对。
- 当前状态：未通过，待实施验证。

### A2 业务-交互线：四个招聘渠道按技能包规则采集岗位
- 业务起点：采集配置选择 BOSS 直聘、猎聘、智联招聘或国聘渠道。
- 触发动作：执行对应渠道采集。
- 关键交互：采集服务按 `E:\内容\岗位skill\岗位采集技能包` 的规则解析岗位名称、企业名称、薪资范围、工作区域等字段。
- 业务终点：每个渠道返回的岗位结果字段满足实例入库与合入所需字段。
- 结果承接：后续实例明细和 `yj_post` 数据可区分来源并保持字段语义一致。
- 核对方式：代码实现对照技能包、局部样例或可用运行验证。
- 当前状态：未通过，待实施验证。

## 技术验收

### T1 技术-接口线：立即采集与定时采集共用一致实例处理入口
- 正式入口：`/admin-api/postcollect/post-collection-task/collect-now` 和定时任务执行入口。
- 支撑的业务结果：两种触发方式都创建任务实例、写入实例明细、完成后执行合入。
- 技术边界：不把立即采集和定时采集做成两套不同状态机。
- 通过条件：代码核对和运行验证证明两种入口均走统一实例链路。
- 证据承接方式：实施记录、验证记录。
- 当前状态：未通过。

### T2 技术-数据线：测试库表结构与数据库说明一致
- 正式入口：`yunjikeji-admin-server/doc/数据库表结构说明.md`。
- 支撑的业务结果：`yj_post`、`yj_post_instance`、`yj_post_collection_task_instance` 字段、索引和租户边界符合最新说明。
- 技术边界：只执行测试库结构调整，不操作生产库。
- 通过条件：测试库元数据查询结果与说明一致，执行记录包含库名、脚本、校验结果。
- 证据承接方式：SQL 脚本、数据库执行记录。
- 当前状态：未通过。

### T3 技术-数据线：正式岗位表按四字段联合去重合入
- 正式入口：采集任务实例完成后的合入逻辑。
- 支撑的业务结果：`yj_post` 中不会重复写入岗位名称、企业名称、薪资范围、工作区域完全相同的采集岗位。
- 技术边界：`yj_post` 不再按租户归属采集岗位；`company_name` 表示采集到的发布岗位公司名称。
- 通过条件：重复样本不会新增正式岗位，非重复样本可写入正式岗位，实例合入数量准确。
- 证据承接方式：单元测试、集成验证或数据库前后对比记录。
- 当前状态：未通过。

### T4 技术-代码线：四渠道实现接入且符合技能包
- 正式入口：岗位采集服务工厂和各 `XXXPlatformPostCollectServiceImpl`。
- 支撑的业务结果：BOSS 直聘、猎聘、智联招聘、国聘均可由配置渠道路由到对应实现。
- 技术边界：不写假采集数据冒充真实机制；外部访问受限时应清晰返回失败边界。
- 通过条件：代码存在、工厂可路由、字段映射与技能包核对通过。
- 证据承接方式：渠道符合性记录、代码 diff、测试记录。
- 当前状态：未通过。
